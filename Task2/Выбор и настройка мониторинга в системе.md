### Мотивация

Мониторинг необходим для понимания горячих точек приложении. 
- Почему медленно отображается информация на UI?
- Почему медленно обрабатываются заказы? 
С помощью мониторинга мы можем увидеть какие компоненты системы ненагружены или же являются бутылочным горлышком. 
Необходимо добавить мониторинг очереди: нет понимания есть ли рост объема сообщений.

### Выбор подхода к мониторингу

Для SHOP API предлагаю использовать RED подход, так как у нас это API представляет из себя классический REST сервис. 
Для MES API предлагаю использовать комбинированный RED и USE подход, 
так как у данного приложений используется комбинированный
профиль нагрузки: 
- USE нам необходим для мониторинга расчёта моделей,
так как этот метод опирается на утилизацию и сатурацию, что необходимо нам для понимания насколько сервис загружен или же наоборот перегружен.
- RED необходим для понимания скорости ответов на запросы чтения и 
его длительности. 
Необходимо настроить Prometheus агента в RabbitMQ. Для Prometheus подойдёт подход USE.
Мы можем посчитать утилизацию очереди в виде размера буфера и ошибочные - необработанные сообщения. 

### Метрики, которые будем использовать
#### Метрики для SHOP API:
- Number of requests (RPS) for internet shop API - чтение в секунду Read
- Number of HTTP 200 for shop API - успех
- Number of HTTP 500 for shop API - ошибка 
- Number of HTTP 500 for shop API / Number of requests (RPS) for internet shop API - Error rate
- Response time (latency) for shop API - длительность ответа для пользователя

#### Метрики для MES API:
- Number of requests (RPS) for internet MES API - чтение в секунду Read
- Number of HTTP 200 for MES API - успех
- Number of HTTP 500 for MES API - ошибка
- Number of HTTP 500 for MES API / Number of requests (RPS) for internet shop API - Error rate
- Response time (latency) for MES API - длительность ответа для пользователя

#### Метрики утилизации MES API: 
- CPU % for MES API
- Memory Utilisation for MES API
- Number of simultanious sessions for MES API

#### Сатурация MES API:
- Memory Utilisation for MES API / Number of simultanious sessions for MES API - доля памяти на сессию оператора. 
Гипотеза: мы хоти посмотреть сколько утилизируется памяти при выполнении запроса на расчёт заказа.
- CPU % for MES API / Number of simultanious sessions for MES API - доля CPU на сессию оператора.
Гипотеза: мы хоти посмотреть сколько утилизируется CPU при выполнении запроса на расчёт заказа.

#### Метрики для RabbitMQ:
- Number of message in flight in RabbitMQ - утилизация очереди.
- Number of dead-letter-exchange letters in RabbitMQ - ошибочные сообщения. Потенциально это "застрявшие" сообщения.

План действий: 
- Развернуть Prometheus
- Внедрить агент для SHOP API для публикации в Prometheus. Проверить, что метрики собираются
- Внедрить агент для MES API для публикации в Prometheus. Проверить, что метрики собираются
- Развернуть Grafana
- Подключить в Grafana источник данных Prometheus. 
- Настроить два дашборда - для SHOP API и MES API
